Résumé : une installation dédiée est bornée par MAXIMUS_INSTALLATION_COMPANY_ID. Le serveur ne doit jamais déduire l’entreprise depuis un companyId envoyé par le navigateur. Le compte créé est company_admin ; aucun maximus_admin global n’est provisionné.

1. Objectif et garanties

Cette procédure installe une copie MAXIMUS destinée à une seule entreprise. Elle convient à un VPS, un serveur local, une machine de recette isolée ou une installation dans le réseau interne du client.

GarantieComportement attendu
EntrepriseL’identifiant MAXIMUS_INSTALLATION_COMPANY_ID fixe le périmètre côté serveur.
ConnexionSeuls les comptes rattachés à l’entreprise configurée peuvent ouvrir une session.
AdministrationLe compte initial est company_admin. L’administration globale MAXIMUS est désactivée.
Routes centralesLes routes réservées à MAXIMUS retournent 404 CENTRAL_INSTALLATION_ONLY.
Vitrine publiqueLes boutiques, domaines, images, profils et parcours Transport d’une autre entreprise retournent 404 INSTALLATION_COMPANY_ONLY.
RelanceLa commande maximus:install-company est idempotente : elle met à jour l’entreprise et le compte dédié sans créer de compte global.
Cette isolation n’est pas un simple masquage d’écran. Elle est appliquée par Laravel, dans le contexte serveur et les middlewares. Ne pas supprimer ces contrôles pour “simplifier” l’interface.

2. Choisir le mode d’installation

dedicated

À choisir pour un VPS ou un cloud réservé à l’entreprise. Le serveur peut être public, avec un domaine et un certificat TLS.

  • Instance séparée.
  • Base PostgreSQL séparée.
  • Stockage séparé.
  • Accès administrateur entreprise seulement.

on_premise

À choisir pour un serveur dans l’infrastructure de l’entreprise, accessible sur réseau interne ou via VPN.

  • Même isolation applicative.
  • Certificat géré par l’entreprise.
  • Sauvegardes sous responsabilité du client.
  • Pare-feu et accès réseau internes.

Le script d’installation interactif initialise le mode dedicated. Pour on_premise, modifier la valeur après la collecte ou fournir la configuration équivalente dans l’environnement avant l’exécution finale. Le serveur de production doit toujours utiliser une valeur explicite et contrôlée.

Stabilité de l’identifiant : conserver le même MAXIMUS_INSTALLATION_COMPANY_ID lors des mises à jour et des relances. Le changer crée un nouveau périmètre logique et peut laisser l’ancien tenant dans la base.

3. Architecture de l’instance isolée

Le workspace contient le frontend React/Vite et l’API Laravel. Le frontend est construit puis copié dans artifacts/api-server/laravel/public. Laravel utilise PostgreSQL pour les comptes, les entreprises, les modules, les sessions et les données métier.

maximus/
├── artifacts/api-server/laravel/   # API Laravel et runtime
│   ├── .env                        # configuration locale, chmod 600
│   ├── public/                     # frontend construit + point d’entrée
│   ├── storage/app/digital-products/
│   └── server.php                  # serveur PHP de test/local
├── artifacts/maximus/              # frontend React/Vite
└── scripts/install-maximus-instance.sh

Flux d’installation

  1. Le script vérifie PHP, Composer et curl.
  2. Il crée ou met à jour le fichier Laravel .env sans supprimer les autres variables.
  3. Il protège le fichier par chmod 600.
  4. Il installe Composer et construit le frontend.
  5. Il prépare les répertoires de stockage et de cache.
  6. Il migre PostgreSQL.
  7. Il exécute php artisan maximus:install-company.
  8. Il lance une sonde temporaire /api/healthz, sauf si elle est désactivée.

5. Préparer PostgreSQL et le stockage

5.1 Base locale PostgreSQL

Exemple Debian/Ubuntu. Utiliser un mot de passe unique, transmis uniquement au prompt sécurisé :

sudo -u postgres createuser --pwprompt maximus
sudo -u postgres createdb --owner=maximus maximus
sudo -u postgres psql -d maximus -c \
  "ALTER ROLE maximus SET client_encoding TO 'UTF8';"

Pour PostgreSQL distant, faire autoriser l’adresse du serveur applicatif dans le pare-feu et dans pg_hba.conf. Ne pas exposer le port 5432 à tout Internet.

5.2 Répertoire applicatif

sudo useradd --system --home /opt/maximus --shell /usr/sbin/nologin maximus || true
sudo mkdir -p /opt/maximus
sudo chown -R maximus:maximus /opt/maximus
cd /opt/maximus

Le compte qui lance l’installateur doit pouvoir écrire dans le workspace. Après installation, le processus HTTP permanent doit utiliser un utilisateur non privilégié et les mêmes permissions sur storage, bootstrap/cache et le stockage numérique.

5.3 Stockage persistant

Le script utilise par défaut artifacts/api-server/laravel/storage/app/digital-products. Ce dossier doit être inclus dans les sauvegardes. Ne pas le remplacer par /tmp ou un disque éphémère.

6. Installer avec le script

6.1 Récupérer le code

git clone <depot-prive> /opt/maximus
cd /opt/maximus
chmod +x scripts/install-maximus-instance.sh
./scripts/install-maximus-instance.sh --help

6.2 Installation interactive recommandée

./scripts/install-maximus-instance.sh

Les secrets sont demandés sans être affichés. Les valeurs déjà présentes dans l’environnement ou dans le .env sont réutilisées. Les variables non liées à l’installation sont conservées.

6.3 Valeurs demandées

  1. Identifiant stable : lettres, chiffres, tiret ou underscore.
  2. Entreprise : nom, responsable, email, pays, secteur.
  3. Modules : liste séparée par virgules, par défaut commerce,ecommerce,stocks,presences.
  4. PostgreSQL : hôte, port, base, utilisateur, mot de passe.
  5. Administrateur entreprise : email et mot de passe d’au moins 8 caractères.
  6. URL : URL publique ou URL locale de l’installation.

6.4 Installation non interactive

Ne pas mettre les mots de passe dans les arguments. Les fournir dans l’environnement du processus ou par le gestionnaire de secrets du serveur :

export MAXIMUS_DEPLOYMENT_MODE=dedicated
export MAXIMUS_INSTALLATION_COMPANY_ID=entreprise-exemple
export MAXIMUS_COMPANY_NAME='Entreprise Exemple'
export MAXIMUS_COMPANY_MANAGER='Responsable Exemple'
export MAXIMUS_COMPANY_EMAIL='contact@example.test'
export MAXIMUS_ADMIN_USER='admin@example.test'
read -r -s MAXIMUS_ADMIN_PASSWORD
export MAXIMUS_ADMIN_PASSWORD
read -r -s DB_PASSWORD
export DB_PASSWORD
export DB_HOST=127.0.0.1 DB_PORT=5432
export DB_DATABASE=maximus DB_USERNAME=maximus
export APP_URL=https://erp.example.test
export MAXIMUS_INSTALLATION_MODULES=commerce,ecommerce,stocks,presences

./scripts/install-maximus-instance.sh --non-interactive

Pour une installation on-premise, utiliser MAXIMUS_DEPLOYMENT_MODE=on_premise. Tester la valeur effective dans /api/installation après démarrage.

8. Démarrer l’application

8.1 Test local temporaire

cd /opt/maximus/artifacts/api-server/laravel
php -S 127.0.0.1:8080 server.php

Dans un autre terminal :

curl -fsS http://127.0.0.1:8080/api/healthz
curl -fsS http://127.0.0.1:8080/api/installation

Le serveur PHP intégré sert à valider l’installation. Il n’est pas recommandé comme exposition Internet permanente.

8.2 Production derrière HTTPS

Utiliser un service supervisé, un utilisateur non privilégié et un reverse proxy HTTPS (Nginx, Apache ou équivalent). Le proxy doit transmettre le host et le protocole d’origine, et ne doit pas rendre PostgreSQL ou le port interne public.

  • Le proxy public écoute sur 443.
  • L’application écoute seulement sur loopback ou sur le réseau privé.
  • Le certificat couvre exactement APP_URL.
  • SESSION_SECURE_COOKIE=true si l’URL commence par HTTPS.
  • Les logs du proxy ne contiennent pas les mots de passe ni les cookies.

8.3 Démarrage contrôlé

Le dépôt ne fournit pas automatiquement un service systemd ou une configuration Nginx : ils dépendent de la distribution, du chemin d’installation et de la politique d’exploitation. Ils doivent être ajoutés par l’administrateur du serveur avant de considérer l’instance comme production.

9. Accès administrateur entreprise

  1. Ouvrir l’URL configurée dans APP_URL.
  2. Utiliser l’email MAXIMUS_ADMIN_USER.
  3. Se connecter avec le mot de passe fourni à l’installateur.
  4. Vérifier que le compte affiche le rôle company_admin et la bonne entreprise.
  5. Créer ensuite les employés et les rôles depuis Organisation.

Une relance de maximus:install-company met à jour le compte dédié et invalide ses sessions existantes. L’opération est utile après une rotation de mot de passe, mais elle doit être planifiée.

cd /opt/maximus/artifacts/api-server/laravel
php artisan config:clear --no-interaction
php artisan maximus:install-company --no-interaction
Ne pas exécuter php artisan maximus:provision-admin sur cette instance. Cette commande est réservée à l’installation centrale et refuse normalement le mode isolé.

10. Validation complète de l’isolation

10.1 Santé et identité

curl -fsS https://erp.example.test/api/healthz
curl -fsS https://erp.example.test/api/installation

Vérifier : ready=true, companyOnly=true, le mode dedicated ou on_premise, l’identifiant de l’entreprise attendu et adminLoginEnabled=false.

10.2 Routes centrales

Les routes d’inscription publique, catalogue plateforme, contrôle et administration MAXIMUS doivent retourner 404 CENTRAL_INSTALLATION_ONLY. Un masquage dans le menu ne suffit pas comme test.

10.3 Données d’une autre entreprise

Avec deux entreprises de test en base, essayer le slug, les images, le domaine et Transport de l’autre entreprise :

curl -i https://erp.example.test/api/shop/autre-entreprise
curl -i https://erp.example.test/api/shop/autre-entreprise/transport/settings
curl -i https://erp.example.test/api/product-images/autre-entreprise/image.png
curl -i https://erp.example.test/api/company-profile-images/autre-entreprise/profile.png

Les réponses doivent être 404 avec le code INSTALLATION_COMPANY_ONLY. La boutique et les ressources de l’entreprise configurée doivent, elles, rester accessibles.

10.4 Connexion

  • Le company_admin dédié se connecte.
  • Un compte global MAXIMUS ne se connecte pas.
  • Une session d’une autre entreprise est refusée.
  • Après rafraîchissement, la session reste attachée au bon tenant.
  • Un accès direct à une route non autorisée est refusé côté API.

11. Sauvegardes, mises à jour et restauration

11.1 Sauvegarder la base

mkdir -p /var/backups/maximus
pg_dump --format=custom \
  --file=/var/backups/maximus/maximus-$(date +%F-%H%M).dump \
  --host="$DB_HOST" --port="$DB_PORT" \
  --username="$DB_USERNAME" "$DB_DATABASE"
chmod 600 /var/backups/maximus/*.dump

Copier les dumps vers un stockage hors serveur. Tester une restauration sur une base séparée ; une sauvegarde jamais restaurée n’est pas une procédure validée.

11.2 Sauvegarder les fichiers

tar -C artifacts/api-server/laravel/storage/app \
  -czf /var/backups/maximus/digital-products-$(date +%F-%H%M).tar.gz \
  digital-products

Conserver base et fichiers issus du même point de sauvegarde lorsque les commandes ou produits numériques se référencent.

11.3 Mise à jour

cd /opt/maximus
git fetch --all --tags
git checkout <version-validee>
./scripts/install-maximus-instance.sh --skip-healthcheck
cd artifacts/api-server/laravel
php artisan migrate --force --no-interaction

Si l’installateur doit être relancé en non-interactif, fournir les secrets via l’environnement sécurisé. Vérifier ensuite le healthcheck, le mode d’installation, la connexion et les ressources publiques.

11.4 Retour arrière

  1. Arrêter le trafic applicatif.
  2. Conserver les logs et l’état de la base.
  3. Revenir au code validé précédent.
  4. Restaurer la base seulement si nécessaire et si le dump est compatible.
  5. Restaurer les fichiers numériques associés.
  6. Relancer les validations d’identité, de connexion et d’isolation.

13. Checklist de mise en service

  • Le serveur est dédié à l’entreprise ou séparé par une frontière réseau claire.
  • MAXIMUS_DEPLOYMENT_MODE vaut dedicated ou on_premise.
  • MAXIMUS_INSTALLATION_COMPANY_ID est stable et documenté hors du code.
  • La base PostgreSQL est séparée et protégée par pare-feu.
  • Le fichier .env est en permission 600.
  • APP_KEY est défini et sauvegardé dans le gestionnaire de secrets.
  • Le frontend a été construit et copié dans Laravel.
  • Le stockage numérique est persistant et sauvegardé.
  • Le service permanent utilise un utilisateur non privilégié.
  • Le reverse proxy sert HTTPS et protège le port interne.
  • /api/healthz répond correctement.
  • /api/installation confirme le bon mode et le bon tenant.
  • Le compte company_admin se connecte.
  • Aucun compte maximus_admin global n’a été créé.
  • Les routes centrales sont refusées.
  • Les boutiques, images et parcours Transport d’autres entreprises sont refusés.
  • Une sauvegarde PostgreSQL et une restauration de test ont été réalisées.
  • La procédure de mise à jour et de retour arrière est connue de l’exploitant.
Installation dédiée conforme : l’entreprise configurée peut administrer ses modules et ses données ; les autres tenants, l’administration globale et les ressources publiques étrangères restent inaccessibles côté serveur.
