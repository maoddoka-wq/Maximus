Résumé : l’entreprise est créée, validée et équipée depuis MAXIMUS principal. Le VPS dédié s’enrôle avec un fichier JSON contenant un secret conservé jusqu’à révocation, récupère la configuration autorisée et se resynchronise ensuite par HTTPS. Le compte local créé est company_admin ; aucun maximus_admin global n’est provisionné.
Compatibilité non universelle : les installateurs fournis ciblent Debian/Ubuntu avec Nginx et PHP-FPM 8.2, ou Windows Server 2019+ 64 bits avec IIS et PHP 8.2 NTS. Windows 10/11, les autres distributions, Apache, l’hébergement mutualisé et les conteneurs ne sont pas couverts par ces scripts. Les scripts LAN ne rendent pas une instance accessible publiquement sur Internet. Un serveur hors de cette matrice exige une adaptation et des tests dédiés avant mise en service.

1. Règle de lecture : qui fait quoi et quand

Ne pas mélanger les deux serveurs. Les actions marquées MAXIMUS PRINCIPAL se font dans l’interface et la base du MAXIMUS central. Les actions marquées SERVEUR DÉDIÉ se font dans le terminal du VPS de l’entreprise. Une commande destinée au serveur dédié ne doit jamais être exécutée dans le terminal du serveur central, et inversement.
MomentMAXIMUS principalServeur dédié de l’entreprise

1.2 Chronologie obligatoire

  1. J−1 ou avant : l’exploitant prépare le DNS du futur VPS et la base PostgreSQL.
  2. Étape A : l’administrateur MAXIMUS crée et active l’entreprise centrale.
  3. Étape B : l’administrateur MAXIMUS prépare l’installation et télécharge le bootstrap.
  4. Étape C : l’exploitant transfère le bootstrap au seul VPS concerné.
  5. Étape D : l’exploitant lance l’installation automatisée.
  6. Étape E : l’exploitant démarre le service web et valide les URL de santé et d’identité.
  7. Étape F : l’exploitant installe la synchronisation planifiée.
  8. Après chaque changement central : l’administrateur publie le changement, puis l’exploitant déclenche une synchronisation immédiate si le changement ne peut pas attendre le prochain créneau.

2. Objectif et garanties

Cette procédure installe une copie MAXIMUS destinée à une seule entreprise. Elle convient à un VPS, un serveur local, une machine de recette isolée ou une installation dans le réseau interne du client.

GarantieComportement attendu
EntrepriseL’identifiant reçu par l’enrôlement central fixe le périmètre côté serveur.
ConnexionSeuls les comptes rattachés à l’entreprise configurée peuvent ouvrir une session.
AdministrationLe compte initial est company_admin. L’administration globale MAXIMUS est désactivée.
Routes centralesLes routes réservées à MAXIMUS retournent 404 CENTRAL_INSTALLATION_ONLY.
Vitrine publiqueLes boutiques, domaines, images, profils et parcours Transport d’une autre entreprise retournent 404 INSTALLATION_COMPANY_ONLY.
AutoritéMAXIMUS principal reste la source de vérité pour les modules, packs, permissions et domaines.

Cette isolation n’est pas un simple masquage d’écran. Elle est appliquée par Laravel, dans le contexte serveur et les middlewares. Ne pas supprimer ces contrôles pour “simplifier” l’interface.

3. Choisir le mode d’installation

dedicated

À choisir pour un VPS ou un cloud réservé à l’entreprise. Le serveur peut être public, avec un domaine et un certificat TLS.

  • Instance séparée.
  • Base PostgreSQL séparée.
  • Stockage séparé.
  • Accès administrateur entreprise seulement.

on_premise

À choisir pour un serveur dans l’infrastructure de l’entreprise, accessible sur réseau interne ou via VPN.

  • Même isolation applicative.
  • Certificat géré par l’entreprise.
  • Sauvegardes sous responsabilité du client.
  • Pare-feu et accès réseau internes.

Le script utilise le mode inscrit dans le fichier d’enrôlement. MAXIMUS principal choisit explicitement dedicated ou on_premise.

Jeton secret : le fichier d’enrôlement contient un jeton réutilisable jusqu’à sa révocation. Le transférer uniquement au VPS concerné, le supprimer après avoir copié sa valeur dans le gestionnaire de secrets du serveur, et le régénérer depuis MAXIMUS en cas de fuite.

4. Architecture de l’instance isolée

Le workspace contient le frontend React/Vite et l’API Laravel. Le frontend est construit puis copié dans artifacts/api-server/laravel/public. Laravel utilise PostgreSQL pour les comptes, les entreprises, les modules, les sessions et les données métier.

maximus/
├── artifacts/api-server/laravel/   # API Laravel et runtime
│   ├── .env                        # configuration locale, chmod 600
│   ├── public/                     # frontend construit + point d’entrée
│   ├── storage/app/digital-products/
│   └── server.php                  # serveur PHP de test/local
├── artifacts/maximus/              # frontend React/Vite
└── scripts/install-maximus-instance.sh

Flux d’installation

  1. L’administrateur crée et active l’entreprise dans MAXIMUS principal.
  2. Il ouvre sa fiche, choisit « Préparer le VPS dédié » ou « Préparer l’installation locale » et télécharge le JSON.
  3. Le script vérifie PHP, Composer, curl et le JSON d’enrôlement.
  4. Il crée ou met à jour le fichier Laravel .env, y conserve le lien central et protège le fichier par chmod 600.
  5. Il installe Composer, construit le frontend et migre PostgreSQL.
  6. maximus:install-company appelle MAXIMUS principal, valide le jeton, copie l’entreprise, les modules et les domaines, puis crée le company_admin.
  7. Une tâche planifiée lance ensuite maximus:sync-central-installation.
  8. Il lance une sonde temporaire /api/healthz, sauf si elle est désactivée.

6. Préparer PostgreSQL et le stockage

6.1 Base locale PostgreSQL

Exemple Debian/Ubuntu. Utiliser un mot de passe unique, transmis uniquement au prompt sécurisé :

sudo -u postgres createuser --pwprompt maximus
sudo -u postgres createdb --owner=maximus maximus
sudo -u postgres psql -d maximus -c \
  "ALTER ROLE maximus SET client_encoding TO 'UTF8';"

Pour PostgreSQL distant, faire autoriser l’adresse du serveur applicatif dans le pare-feu et dans pg_hba.conf. Ne pas exposer le port 5432 à tout Internet.

6.2 Répertoire applicatif

sudo useradd --system --home /opt/maximus --shell /usr/sbin/nologin maximus || true
sudo mkdir -p /opt/maximus
sudo chown -R maximus:maximus /opt/maximus
cd /opt/maximus

Le compte qui lance l’installateur doit pouvoir écrire dans le workspace. Après installation, le processus HTTP permanent doit utiliser un utilisateur non privilégié et les mêmes permissions sur storage, bootstrap/cache et le stockage numérique.

6.3 Stockage persistant

Le script utilise par défaut artifacts/api-server/laravel/storage/app/digital-products. Ce dossier doit être inclus dans les sauvegardes. Ne pas le remplacer par /tmp ou un disque éphémère.

7. Préparer l’entreprise dans MAXIMUS principal

Cette section est exécutée uniquement par l’administrateur MAXIMUS principal. Le responsable du VPS ne doit pas inventer le nom de l’entreprise, les modules ou les permissions dans le fichier .env.

7.1 Créer ou ouvrir l’entreprise

  1. Ouvrir l’URL du MAXIMUS principal.
  2. Se connecter avec un compte ayant le rôle maximus_admin.
  3. Ouvrir l’espace Entreprises.
  4. Créer l’entreprise ou ouvrir l’entreprise déjà créée.
  5. Vérifier le nom, le responsable, l’email, le pays et le secteur.
  6. Vérifier que son statut est ACTIF. Une entreprise PENDING, REJETÉE, SUSPENDU ou supprimée ne doit pas être enrôlée.

7.2 Configurer exactement le périmètre

  1. Choisir uniquement les modules publiés qui doivent être disponibles sur l’installation.
  2. Pour chaque module, choisir les packs publiés nécessaires.
  3. Choisir les fonctionnalités nécessaires.
  4. Pour chaque fonctionnalité, attribuer les permissions voulues.
  5. Enregistrer et publier la configuration avant de préparer le VPS.
  6. Vérifier le manifeste d’installation avec le bouton Télécharger le manifeste d’installation. Ce manifeste sert à contrôler les choix, mais il ne remplace pas le bootstrap secret.

Le manifeste de contrôle peut être conservé dans le dossier de livraison. Le bootstrap, lui, contient le jeton secret et doit rester strictement confidentiel.

7.3 Générer le bootstrap du serveur

  1. Dans la fiche de l’entreprise, cliquer sur Préparer le VPS dédié pour un serveur public dédié, ou sur Préparer l’installation locale pour un serveur interne/on-premise.
  2. Le serveur central crée ou renouvelle l’enregistrement maximus_installations.
  3. Le navigateur télécharge un fichier nommé suivant le modèle maximus-bootstrap-<companyId>-<mode>.json.
  4. Ouvrir le fichier uniquement pour vérifier sa structure, jamais pour copier son jeton dans un document ou une conversation.
  5. Transférer le fichier au responsable du VPS par un canal privé.
{
  "centralUrl": "https://central.example.test",
  "installationId": "installation-...",
  "companyId": "company-...",
  "mode": "dedicated",
  "token": "<SECRET-A-CONSERVER>"
}
Quand régénérer : si le fichier a été envoyé à la mauvaise personne, copié dans Git, affiché dans un log, perdu, ou si le serveur doit être réinstallé avec un nouveau lien. La régénération remplace le hash du jeton central : l’ancien jeton cesse alors de fonctionner.

8. Installer avec le script

Cette section est exécutée uniquement sur le serveur dédié. Le serveur dédié doit pouvoir ouvrir une connexion HTTPS sortante vers MAXIMUS_CENTRAL_URL. Il n’a pas besoin d’ouvrir PostgreSQL sur Internet et MAXIMUS principal n’a pas besoin d’ouvrir une connexion entrante vers PostgreSQL.

8.0 Transférer le bootstrap sans exposer le secret

Depuis le poste où le fichier a été téléchargé, le transférer directement vers le VPS par un canal SSH privé. Remplacer les valeurs entre chevrons ; ne jamais remplacer <SECRET> dans une commande car le secret est déjà dans le fichier.

scp ./maximus-bootstrap-<companyId>-dedicated.json \
  <utilisateur-vps>@<ip-ou-nom-du-vps>:/tmp/maximus-bootstrap.json

ssh <utilisateur-vps>@<ip-ou-nom-du-vps>
sudo install -d -m 750 -o maximus -g maximus /opt/maximus-secrets
sudo install -m 600 -o maximus -g maximus /tmp/maximus-bootstrap.json \
  /opt/maximus-secrets/bootstrap.json
rm -f /tmp/maximus-bootstrap.json

Si le compte maximus n’existe pas encore, exécuter d’abord les commandes de la section 6.2. Le fichier final doit être lisible par l’utilisateur qui exécute l’installateur, puis supprimé dès que la valeur a été conservée dans le gestionnaire de secrets.

Sur Windows, déposer le bootstrap dans un dossier protégé par les permissions NTFS, par exemple C:\ProgramData\MAXIMUS\bootstrap.json. Ne pas le placer dans le dépôt Git, un dossier partagé avec les employés ou un répertoire web. Dans Git Bash, son chemin s’écrit par exemple /c/ProgramData/MAXIMUS/bootstrap.json.

8.1 Récupérer le code

git clone <depot-prive> /opt/maximus
cd /opt/maximus
chmod +x scripts/install-maximus-instance.sh
./scripts/install-maximus-instance.sh --help

Sur Windows, faire cette étape dans Git Bash, pas dans PowerShell : le fichier install-maximus-instance.sh est le premier installateur à lancer sur les deux systèmes. PowerShell servira ensuite à configurer IIS avec le script .ps1.

8.2 Installer le JSON d’enrôlement

Copier le fichier téléchargé depuis MAXIMUS principal sur le VPS, avec des permissions privées :

chmod 600 /opt/maximus-secrets/bootstrap.json
cd /opt/maximus
./scripts/install-maximus-instance.sh \
  --bootstrap-file /opt/maximus-secrets/bootstrap.json

Le script ne demande plus le nom, l’email, les modules ou les permissions de l’entreprise : ces valeurs sont récupérées depuis MAXIMUS principal.

8.3 Installation non interactive

Ne pas mettre les jetons ni les mots de passe dans les arguments. Les fournir dans l’environnement du processus ou par le gestionnaire de secrets du serveur :

export MAXIMUS_INSTALLATION_BOOTSTRAP=/opt/maximus/maximus-bootstrap.json
export MAXIMUS_ADMIN_USER='admin@example.test'
read -r -s MAXIMUS_ADMIN_PASSWORD
export MAXIMUS_ADMIN_PASSWORD
read -r -s DB_PASSWORD
export DB_PASSWORD
export DB_HOST=127.0.0.1 DB_PORT=5432
 export DB_DATABASE=maximus DB_USERNAME=maximus
 export APP_URL=https://erp.example.test

 ./scripts/install-maximus-instance.sh \
   --bootstrap-file /opt/maximus-secrets/bootstrap.json \
   --non-interactive

Pour une installation on-premise, générer le bootstrap avec le bouton « Préparer l’installation locale ». Tester la valeur effective dans /api/installation après démarrage.

10. Démarrer l’application

10.1 Test local temporaire avant ouverture publique

cd /opt/maximus/artifacts/api-server/laravel
php -S 127.0.0.1:8080 server.php

Dans un autre terminal :

curl -fsS http://127.0.0.1:8080/api/healthz
curl -fsS http://127.0.0.1:8080/api/installation

Ce serveur PHP intégré est réservé à un contrôle temporaire sur loopback. Il ne convient pas à un usage permanent ni à plusieurs employés.

10.2 Préparer le serveur LAN

  • Utiliser une installation MAXIMUS dédiée, avec APP_ENV=production, APP_DEBUG=false, DB_CONNECTION=pgsql, SESSION_SECURE_COOKIE=true et APP_URL=https://<nom-interne>.
  • Installer PostgreSQL localement ou sur un réseau privé; ne jamais ouvrir son port au LAN utilisateur. Le fichier .env doit déjà pointer vers cette base.
  • Réserver une adresse IP locale et faire résoudre le nom DNS interne vers cette IP. Le nom doit être couvert par le certificat TLS et l’autorité de certification doit être approuvée par le serveur et les postes employés.
  • Compiler le frontend et conserver public/index.html, public/index.php ainsi que vendor/ dans l’installation.
  • Contrôler les règles de pare-feu déjà présentes. Les installateurs ajoutent une règle HTTPS limitée au CIDR fourni, mais ne peuvent pas neutraliser une autre règle plus large.
Capacité : le nombre de workers est le maximum de requêtes PHP simultanées, pas le nombre de comptes employés. Le contrôle réserve de la mémoire et des connexions PostgreSQL selon les valeurs fournies; il ne certifie pas les performances sans mesure sur le matériel réel.

10.3 Installer sur Debian ou Ubuntu (Nginx et PHP-FPM)

Installer d’abord Nginx, PHP 8.2 avec PHP-FPM et les extensions Laravel/PostgreSQL requises. Préparer le certificat PEM et sa clé privée; la clé doit être lisible uniquement par root. Le script n’installe ni paquets ni certificat et n’expose aucun serveur PHP intégré.

sudo bash scripts/install-maximus-lan-linux.sh --help
sudo bash scripts/install-maximus-lan-linux.sh \
  --lan-ip <IPv4-du-serveur> \
  --lan-cidr <CIDR-des-employés> \
  --hostname <nom-DNS-interne> \
  --tls-cert <chemin-absolu-du-certificat-ou-fullchain> \
  --tls-key <chemin-absolu-de-la-clé-privée> \
  --run-as-user <compte-Linux-de-l’application> \
  --php-workers <workers-validés-par-la-RAM> \
  --worker-memory-mb <plafond-mémoire-par-worker> \
  --system-db-reserve-mb <réserve-RAM-OS-et-PostgreSQL> \
  --db-reserve <connexions-réservées-hors-web> \
  --request-body-mb <limite-de-requête>

Le script vérifie le CIDR, l’IP locale, le DNS, le certificat et sa clé, l’URL, le mode de déploiement, le budget PostgreSQL et les permissions. Il écrit un pool PHP-FPM dimensionné, configure le routage API vers Laravel, les routes React profondes vers index.html, les 404 des ressources statiques manquantes, puis teste la configuration Nginx et la sonde HTTPS.

Si UFW est déjà actif, une autorisation limitée au CIDR est ajoutée pour HTTPS vers l’IP LAN. Vérifier aussi les règles antérieures et le pare-feu réseau de l’entreprise.

10.4 Installer sur Windows Server (IIS et PHP FastCGI)

Avant cette étape, terminer les sections 5 à 8 dans Git Bash sur le serveur Windows : cela installe les dépendances, construit le frontend, prépare PostgreSQL et crée le compte company_admin. Lancer ensuite le script ci-dessous dans une fenêtre PowerShell 64 bits ouverte comme administrateur. Ne pas lancer le serveur de test php -S pour servir les employés.

Le script cible Windows Server 2019 ou plus récent, IIS avec CGI et URL Rewrite, et PHP 8.2 NTS déjà installé. php-cgi.exe et php.exe doivent provenir du même dossier et charger leur php.ini réel; les extensions PDO PostgreSQL, mbstring, fileinfo et OpenSSL sont requises. Importer le certificat avec clé privée dans Cert:\LocalMachine\My et noter son empreinte.

.\scripts\install-maximus-lan-windows-iis.ps1 `
  -WorkspaceDir '<racine-du-dépôt-MAXIMUS>' `
  -LanIp '<IPv4-du-serveur>' `
  -LanCidr '<CIDR-des-employés>' `
  -InternalHostname '<nom-DNS-interne>' `
  -CertificateThumbprint '<empreinte-du-certificat>' `
  -PhpCgiPath '<chemin-vers-php-cgi.exe>' `
  -PhpWorkerCount <workers-validés-par-la-RAM> `
  -PerWorkerMemoryCapMb <plafond-mémoire-par-worker> `
  -SystemReserveMb <réserve-RAM-du-système> `
  -DbReserveMb <réserve-RAM-de-PostgreSQL> `
  -DbConnectionReserve <connexions-réservées-hors-web> `
  -RequestBodyLimitMb <limite-de-requête> `
  -WhatIf

Remplacer chaque valeur entre chevrons; elles ne sont pas des paramètres par défaut. -WhatIf valide les prérequis statiques sans écrire de configuration. Après revue, relancer la même commande sans -WhatIf : le script effectue alors le précontrôle PostgreSQL, sauvegarde la configuration IIS ainsi que les éventuels web.config et .user.ini, configure FastCGI, les règles de routage SPA/API, la liaison TLS SNI, les ACL et une règle pare-feu limitée au CIDR, puis teste /api/healthz. Le nombre maximal d’instances FastCGI est défini sur le binaire php-cgi.exe : si d’autres sites IIS l’utilisent, ils partagent cette limite; réserver un runtime PHP distinct à MAXIMUS pour les isoler.

Dans les deux systèmes, l’adresse doit rester joignable uniquement depuis le réseau d’entreprise. Les routes React profondes servent index.html; /api et /up passent par Laravel; un fichier statique manquant reste une 404.

10.5 Programmer la synchronisation

L’installateur principal enregistre automatiquement le scheduler, sauf si --skip-scheduler est utilisé. Il lance la vérification Laravel toutes les cinq minutes; c’est ce qui récupère les modules, permissions et domaines publiés par MAXIMUS principal. Sous Linux, le déclencheur utilise cron. Sous Windows, Git Bash délègue au Planificateur de tâches Windows; la tâche est cachée et son journal se trouve dans storage/logs/installation-scheduler.log.

Si le scheduler a été sauté ou doit être recréé, utiliser la commande correspondant au serveur :

sudo -u maximus /opt/maximus/scripts/register-maximus-sync.sh \
  --workspace-dir /opt/maximus --interval-minutes 5
.\scripts\register-maximus-sync.ps1 `
  -WorkspaceDir 'C:\MAXIMUS' -IntervalMinutes 5

Vérifier le scheduler Linux avec sudo -u maximus crontab -l, ou la tâche Windows dans le Planificateur de tâches sous le nom MAXIMUS central scheduler. Après une publication urgente, lancer une synchronisation manuelle :

cd /opt/maximus/artifacts/api-server/laravel
sudo -u maximus php artisan maximus:sync-central-installation
tail -50 storage/logs/installation-scheduler.log
Set-Location C:\MAXIMUS\artifacts\api-server\laravel
php artisan maximus:sync-central-installation

Une synchronisation réussie ne redémarre pas le serveur web. Si elle échoue, garder le journal et corriger la connexion sortante HTTPS vers MAXIMUS principal.

Quand synchroniser : immédiatement après une publication de module, pack, fonctionnalité, permission ou domaine si le changement ne peut pas attendre; sinon au prochain passage automatique, dans un délai maximal de cinq minutes.

11. Accès administrateur entreprise

  1. Ouvrir l’URL configurée dans APP_URL.
  2. Utiliser l’email MAXIMUS_ADMIN_USER.
  3. Se connecter avec le mot de passe fourni à l’installateur.
  4. Vérifier que le compte affiche le rôle company_admin et la bonne entreprise.
  5. Créer ensuite les employés et les rôles depuis Organisation.

Les employés, secteurs, rôles et données métier sont ensuite créés localement par le company_admin. Ils ne sont pas envoyés à MAXIMUS principal par la synchronisation de configuration.

Une relance de maximus:install-company met à jour le compte dédié et invalide ses sessions existantes. L’opération est utile après une rotation de mot de passe, mais elle doit être planifiée.

cd /opt/maximus/artifacts/api-server/laravel
php artisan config:clear --no-interaction
php artisan maximus:install-company --no-interaction
Ne pas exécuter php artisan maximus:provision-admin sur cette instance. Cette commande est réservée à l’installation centrale et refuse normalement le mode isolé.

12.1 Procédure de synchronisation manuelle

cd /opt/maximus/artifacts/api-server/laravel

La commande doit afficher une ligne de succès indiquant que la configuration centrale a été synchronisée. Une synchronisation normale ne nécessite pas de redémarrer Nginx, PHP-FPM ou IIS. Si la commande échoue, conserver le message d’erreur, ne pas supprimer la base locale et suivre la section 15.

13. Validation complète de l’isolation

13.1 Santé et identité

curl -fsS https://erp.example.test/api/healthz
curl -fsS https://erp.example.test/api/installation

Vérifier : ready=true, companyOnly=true, le mode dedicated ou on_premise, l’identifiant de l’entreprise attendu et adminLoginEnabled=false.

13.2 Routes centrales

Les routes d’inscription publique, catalogue plateforme, contrôle et administration MAXIMUS doivent retourner 404 CENTRAL_INSTALLATION_ONLY. Un masquage dans le menu ne suffit pas comme test.

13.3 Données d’une autre entreprise

Avec deux entreprises de test en base, essayer le slug, les images, le domaine et Transport de l’autre entreprise :

curl -i https://erp.example.test/api/shop/autre-entreprise
curl -i https://erp.example.test/api/shop/autre-entreprise/transport/settings
curl -i https://erp.example.test/api/product-images/autre-entreprise/image.png
curl -i https://erp.example.test/api/company-profile-images/autre-entreprise/profile.png

Les réponses doivent être 404 avec le code INSTALLATION_COMPANY_ONLY. La boutique et les ressources de l’entreprise configurée doivent, elles, rester accessibles.

13.4 Connexion

  • Le company_admin dédié se connecte.
  • Un compte global MAXIMUS ne se connecte pas.
  • Une session d’une autre entreprise est refusée.
  • Après rafraîchissement, la session reste attachée au bon tenant.
  • Un accès direct à une route non autorisée est refusé côté API.

14. Sauvegardes, mises à jour et restauration

14.1 Sauvegarder la base

mkdir -p /var/backups/maximus
pg_dump --format=custom \
  --file=/var/backups/maximus/maximus-$(date +%F-%H%M).dump \
  --host="$DB_HOST" --port="$DB_PORT" \
  --username="$DB_USERNAME" "$DB_DATABASE"
chmod 600 /var/backups/maximus/*.dump

Copier les dumps vers un stockage hors serveur. Tester une restauration sur une base séparée ; une sauvegarde jamais restaurée n’est pas une procédure validée.

14.2 Sauvegarder les fichiers

tar -C artifacts/api-server/laravel/storage/app \
  -czf /var/backups/maximus/digital-products-$(date +%F-%H%M).tar.gz \
  digital-products

Conserver base et fichiers issus du même point de sauvegarde lorsque les commandes ou produits numériques se référencent.

14.3 Mise à jour

cd /opt/maximus
git fetch --all --tags
git checkout <version-validee>
./scripts/install-maximus-instance.sh --skip-healthcheck
cd artifacts/api-server/laravel
php artisan migrate --force --no-interaction

Si l’installateur doit être relancé en non-interactif, fournir les secrets via l’environnement sécurisé. Vérifier ensuite le healthcheck, le mode d’installation, la connexion et les ressources publiques.

14.4 Retour arrière

  1. Arrêter le trafic applicatif.
  2. Conserver les logs et l’état de la base.
  3. Revenir au code validé précédent.
  4. Restaurer la base seulement si nécessaire et si le dump est compatible.
  5. Restaurer les fichiers numériques associés.
  6. Relancer les validations d’identité, de connexion et d’isolation.

16. Checklist de mise en service

  • La version exacte du système correspond à la matrice prise en charge de la section 5.1.
  • L’installation a été exécutée sur le serveur cible; une réussite sur le PC de test ou dans l’environnement de développement ne suffit pas.
  • Le nombre de workers et les limites PostgreSQL ont été choisis après mesure de la mémoire, des connexions et de la charge attendue.
  • Le serveur est dédié à l’entreprise ou séparé par une frontière réseau claire.
  • MAXIMUS_DEPLOYMENT_MODE vaut dedicated ou on_premise.
  • Le fichier bootstrap a été généré par MAXIMUS principal et supprimé ou protégé après installation.
  • MAXIMUS_CENTRAL_URL, MAXIMUS_INSTALLATION_ID et le jeton sont présents dans le fichier privé .env.
  • La synchronisation centrale fonctionne avec php artisan maximus:sync-central-installation.
  • La base PostgreSQL est séparée et protégée par pare-feu.
  • Le fichier .env est en permission 600.
  • APP_KEY est défini et sauvegardé dans le gestionnaire de secrets.
  • Le frontend a été construit et copié dans Laravel.
  • Le stockage numérique est persistant et sauvegardé.
  • PHP-FPM ou le pool IIS s’exécute sous une identité d’application non privilégiée; le fichier .env n’est pas lisible par les employés.
  • Nginx ou IIS sert HTTPS sur l’adresse LAN prévue, avec une règle de pare-feu limitée au CIDR employé.
  • /api/healthz répond correctement.
  • /api/installation confirme le bon mode et le bon tenant.
  • Le compte company_admin se connecte.
  • Aucun compte maximus_admin global n’a été créé.
  • Les routes centrales sont refusées.
  • Les boutiques, images et parcours Transport d’autres entreprises sont refusés.
  • Une modification de module ou de domaine dans MAXIMUS est visible après synchronisation.
  • Une sauvegarde PostgreSQL et une restauration de test ont été réalisées.
  • Le scheduler a fonctionné après redémarrage du serveur; sous Windows, son compte et son fonctionnement sans session utilisateur ont été vérifiés.
  • La procédure de mise à jour et de retour arrière est connue de l’exploitant.
Installation dédiée conforme : l’entreprise configurée peut administrer ses modules et ses données ; les autres tenants, l’administration globale et les ressources publiques étrangères restent inaccessibles côté serveur.
