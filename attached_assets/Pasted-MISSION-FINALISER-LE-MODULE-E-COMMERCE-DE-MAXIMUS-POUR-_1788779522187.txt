MISSION : FINALISER LE MODULE E-COMMERCE DE MAXIMUS POUR LA PRODUCTION

Je veux maintenant que tu termines complètement le module E-commerce de MAXIMUS.

Je ne veux pas un prototype ni quelques pages supplémentaires.

Je veux un véritable système e-commerce SaaS multi-entreprises, fonctionnel, cohérent, sécurisé, professionnel et préparé pour la production.

IMPORTANT :

NE CASSE PAS LES FONCTIONNALITÉS EXISTANTES DE MAXIMUS.

Avant toute modification, analyse l'implémentation actuelle du module E-commerce et ses dépendances.

Ne modifie pas au hasard les composants partagés, les menus, les permissions ou les autres modules.

Travaille progressivement et teste après chaque partie importante.

10. LIENS PUBLICS — SIMPLIFIER

Je ne veux plus que les liens publics ressemblent à des URLs techniques ou à des URLs générées de manière compliquée.

Le système doit être conçu autour d'une URL publique simple.

Exemple d'architecture souhaitée :

Boutique publique :

"https://boutique.domaine.com"

ou, lorsque le système utilise un domaine principal :

"https://nom-boutique.domaine.com"

Pour le client, l'URL doit être simple, lisible et professionnelle.

Ne jamais afficher :

- URL Render ;
- URL Replit ;
- endpoint API ;
- IDs internes ;
- company_id ;
- identifiants techniques.

---

11. SOUS-DOMAINES — PRÊT POUR LA PRODUCTION

Je veux que le système de sous-domaines des boutiques soit conçu correctement pour la production, et pas comme une simple redirection frontend.

Architecture souhaitée :

Sous-domaine
↓
résolution du domaine
↓
identification de la boutique/entreprise
↓
vérification que la boutique est active
↓
chargement du tenant correspondant
↓
affichage de sa boutique uniquement.

Chaque sous-domaine doit correspondre à UNE boutique.

Exemple conceptuel :

"boutique1.mondomaine.com"
→ entreprise 1

"boutique2.mondomaine.com"
→ entreprise 2

Une entreprise ne doit jamais pouvoir récupérer les données d'une autre.

---

12. IDENTIFICATION DU TENANT PAR DOMAINE

Ne fais jamais confiance à un "company_id" envoyé par le navigateur pour déterminer la boutique.

Le backend doit déterminer la boutique à partir du domaine/sous-domaine reconnu.

Il faut prévoir :

- mapping domaine → entreprise ;
- vérification d'existence ;
- vérification du statut ;
- résolution sécurisée ;
- isolation tenant ;
- gestion des domaines inconnus ;
- gestion d'une boutique inactive ;
- gestion des conflits de sous-domaines.

Les sous-domaines doivent être uniques.

---

13. PRÉPARATION AUX DOMAINES PERSONNALISÉS

Même si les domaines personnalisés ne sont pas encore activés, construis l'architecture de façon à pouvoir supporter plus tard :

"www.maboutique.com"

→ boutique de l'entreprise concernée.

Prévoir conceptuellement :

- domaine système ;
- sous-domaine système ;
- domaine personnalisé ;
- statut du domaine ;
- entreprise associée ;
- vérification du domaine ;
- possibilité future de SSL ;
- suppression/changement du domaine.

Ne mets pas une solution temporaire difficile à remplacer.

---

14. SÉCURITÉ DES SOUS-DOMAINES

- isolation entre boutiques ;

- authentification ;

- cookies ;

Toutes les données e-commerce doivent appartenir au bon tenant.

Vérifie :

- produits ;
- catégories ;
- commandes ;
- clients ;
- paniers ;
- favoris ;
- adresses ;
- paiements ;
- livraisons ;
- paramètres ;

- promotions ;
- domaines ;
- utilisateurs.

Un client ou une entreprise ne doit jamais pouvoir accéder aux données d'un autre tenant en modifiant un ID.

Teste volontairement ce scénario.

L'activation de l'e-commerce ne doit pas créer inutilement des rôles ou unités dans l'organisation.

Si certains éléments sont réellement nécessaires :

- les créer uniquement pour le tenant concerné ;
- une seule fois ;
- de manière idempotente ;
- sans duplication ;
- sans dépendance à une entreprise fictive.
