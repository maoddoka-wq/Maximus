CAHIER D’ARCHITECTURE

Système de paiement MAXIMUS + DiamanoPay

1. OBJECTIF

Créer dans MAXIMUS une infrastructure de paiement centralisée permettant de gérer de manière sécurisée :

- les paiements clients ;
- les encaissements des entreprises ;
- les paiements e-commerce ;
- les commissions ;
- les portefeuilles vendeurs ;
- les remboursements ;
- les demandes de retrait ;
- les reversements aux vendeurs ;
- les abonnements MAXIMUS ;
- les futures fonctionnalités financières.

DiamanoPay constitue la passerelle de paiement externe.

MAXIMUS constitue la couche métier qui orchestre les transactions, les droits, les portefeuilles, les commissions et l'historique financier.

---

2. PRINCIPE FONDAMENTAL

Ne pas construire un système de paiement indépendant dans chaque module.

Architecture :

CLIENT
↓
MODULE MAXIMUS
↓
PAYMENT SERVICE MAXIMUS
↓
DIAMANOPAY
↓
Wave / Orange Money / Carte / autre moyen disponible
↓
Confirmation
↓
Webhook DiamanoPay
↓
MAXIMUS
↓
Ledger financier
↓
Portefeuille concerné
↓
Module métier

DiamanoPay doit être considéré comme le prestataire de paiement.

MAXIMUS doit rester la source de vérité concernant les opérations métier et les écritures internes.

---

3. ARCHITECTURE GÉNÉRALE

L'architecture doit être organisée en couches.

Couche 1 — Interface

React/Vite :

- checkout ;
- paiement ;
- portefeuille ;
- transactions ;
- retraits ;
- remboursements ;
- administration financière.

Le frontend ne communique jamais directement avec les secrets DiamanoPay.

Couche 2 — API MAXIMUS

Laravel/Node selon l'architecture existante :

- PaymentController ;
- PaymentService ;
- WalletService ;
- LedgerService ;
- CommissionService ;
- RefundService ;
- WithdrawalService ;
- WebhookController ;
- PaymentProviderService.

Couche 3 — Provider

Créer une abstraction :

PaymentProviderInterface

Puis :

DiamanoPayProvider

L'objectif est de pouvoir ajouter ultérieurement un autre prestataire sans reconstruire MAXIMUS.

Architecture :

Payment Service
→ Provider Interface
→ DiamanoPay Provider

et éventuellement demain :

Payment Service
→ Wave Provider
ou
→ autre Provider.

---

4. DIAMANOPAY

L'intégration doit respecter strictement la documentation officielle disponible.

DiamanoPay indique actuellement une API avec authentification serveur, création de charge/paiement, webhook et vérification de transaction. Les credentials doivent rester côté backend.

Variables d'environnement recommandées :

DIAMANOPAY_CLIENT_ID
DIAMANOPAY_CLIENT_SECRET
DIAMANOPAY_ACCESS_TOKEN
DIAMANOPAY_BASE_URL
DIAMANOPAY_WEBHOOK_SECRET

Les noms exacts doivent être adaptés à la méthode d'authentification effectivement utilisée par le compte MAXIMUS.

Aucune clé secrète dans :

- React ;
- Vite ;
- localStorage ;
- cookies accessibles au JavaScript ;
- GitHub ;
- logs ;
- réponses API publiques.

7. FLUX DE PAIEMENT

Exemple e-commerce

Client :

Panier = 50 000 FCFA

Étape 1 :

MAXIMUS crée la commande.

Statut :

PENDING_PAYMENT

Étape 2 :

MAXIMUS crée une transaction.

Statut :

PENDING

Étape 3 :

MAXIMUS demande à DiamanoPay d'initialiser le paiement.

Étape 4 :

Le client effectue le paiement.

Étape 5 :

DiamanoPay confirme le résultat.

Étape 6 :

MAXIMUS reçoit le webhook.

Étape 7 :

MAXIMUS vérifie la transaction.

Étape 8 :

La transaction devient :

PAID

Étape 9 :

La commande devient :

PAID

Étape 10 :

MAXIMUS crée les écritures financières.

IMPORTANT :

La redirection du client vers une page « paiement réussi » ne suffit jamais pour créditer le vendeur.

---

8. WEBHOOK

Créer :

POST /api/webhooks/diamanopay

Le webhook doit :

1. recevoir la notification ;
2. vérifier son authenticité ;
3. identifier la transaction ;
4. vérifier le montant ;
5. vérifier la référence ;
6. vérifier le statut ;
7. vérifier le tenant ;
8. empêcher le double traitement ;
9. enregistrer l'événement ;
10. mettre à jour la transaction ;
11. déclencher le traitement métier.

Créer une table :

payment_events

avec :

- id ;
- payment_id ;
- provider ;
- event_type ;
- provider_event_id ;
- payload ;
- signature ;
- processed_at ;
- processing_status ;
- error_message.

Créer une contrainte d'idempotence.

Un même événement reçu plusieurs fois ne doit produire qu'un seul traitement financier.

9. LEDGER FINANCIER

C'est une partie essentielle.

NE PAS gérer les soldes uniquement avec :

balance = balance + montant

Créer un ledger financier.

Table :

ledger_entries

Chaque mouvement possède :

- id ;
- tenant_id ;
- wallet_id ;
- transaction_id ;
- type ;
- direction ;
- amount ;
- currency ;
- reference ;
- description ;
- status ;
- created_at.

Exemples :

PAYMENT_CREDIT
COMMISSION_DEBIT
REFUND_DEBIT
WITHDRAWAL_DEBIT
WITHDRAWAL_REVERSED
ADJUSTMENT

Le ledger doit permettre de reconstituer l'intégralité d'un solde.

---

10. PORTEFEUILLES

Table :

wallets

Un portefeuille peut appartenir à :

- une entreprise ;
- un vendeur ;
- un compte spécifique selon les besoins futurs.

Exemple :

Vendeur A

Solde disponible :
95 000 FCFA

Solde en attente :
20 000 FCFA

Solde retiré :
150 000 FCFA

Les valeurs affichées doivent être calculables à partir des écritures du ledger.

Prévoir également :

available_balance
pending_balance

mais ces valeurs doivent être maintenues de façon transactionnelle et rester cohérentes avec le ledger.

---

15. POINT CRITIQUE : ARGENT REÇU PAR MAXIMUS

Si les paiements des clients arrivent sur le compte marchand DiamanoPay de MAXIMUS, MAXIMUS doit maintenir une séparation comptable interne entre les montants.

Exemple :

DiamanoPay reçoit :

500 000 FCFA

Cela ne signifie pas :

« MAXIMUS possède 500 000 FCFA ».

Le ledger MAXIMUS doit savoir :

Vendeur A : 200 000
Vendeur B : 150 000
Vendeur C : 100 000
Commission MAXIMUS : 50 000

La somme doit rester réconciliable avec les opérations réellement confirmées.

IMPORTANT :

Cette architecture logicielle ne constitue pas à elle seule une qualification juridique des fonds. Avant une mise en production marketplace à grande échelle, valider avec DiamanoPay et, si nécessaire, un conseiller juridique/comptable, les règles applicables à la détention et au reversement des fonds.

28. RÈGLE DE CONCEPTION

MAXIMUS doit fonctionner selon cette séparation :

DIAMANOPAY
= infrastructure externe de paiement

PAYMENT SERVICE
= orchestration des paiements

LEDGER
= historique financier interne

WALLET
= représentation du solde disponible

COMMISSION SERVICE
= calcul des commissions

PAYOUT SERVICE
= gestion des reversements

REFUND SERVICE
= gestion des remboursements

MODULE MÉTIER
= commande, facture, abonnement, vente, etc.

---

29. RÈGLE ABSOLUE

Aucune opération financière ne doit être considérée comme définitive sans confirmation fiable du prestataire.

Aucun solde ne doit être créé artificiellement.

Aucun retrait ne doit être simulé.

Aucun paiement ne doit être marqué « réussi » simplement parce que le frontend affiche une page de succès.

Aucune entreprise ne doit pouvoir accéder aux données financières d'une autre.

Aucune clé secrète ne doit apparaître dans le frontend.

---
