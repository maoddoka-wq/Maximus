# MISSION CRITIQUE — MAXIMUS DOIT ÊTRE CORRIGÉ PROPREMENT, PAS BRICOLÉ

Tu travailles sur **MAXIMUS**, une véritable application SaaS multi-entreprises destinée à être utilisée en production.

Je ne veux plus de corrections superficielles, de faux correctifs, de données fictives, de contournements temporaires ou de modifications faites sans comprendre l’architecture.

**TON OBJECTIF EST DE TROUVER LES CAUSES RÉELLES DES PROBLÈMES, DE LES CORRIGER DANS LE CODE ET LA BASE DE DONNÉES, PUIS DE PROUVER QUE LES CORRECTIONS FONCTIONNENT ET NE CASSERONT PAS À NOUVEAU.**

---

# 1. RÈGLE ABSOLUE : NE PAS BRICOLER

Avant de modifier le code :

1. Analyse toute l’architecture existante.
2. Identifie frontend, backend, API, modèles, migrations, middleware, authentification, permissions, routes, services, contrôleurs, cache et base de données.
3. Identifie comment les entreprises, utilisateurs, administrations, modules, rôles, unités et données e-commerce sont liés.
4. Recherche les vrais flux de données.
5. Reproduis chaque problème.
6. Suis le chemin complet :

Frontend → requête API → route → contrôleur → service → modèle/ORM → base de données → réponse API → état frontend → affichage.

**Ne corrige jamais uniquement l’écran si le problème vient du backend ou de la base de données.**

Si tu ne comprends pas la cause, continue l’analyse avant de modifier.

Interdiction de dire :

* « c’est probablement Replit »
* « ça fonctionne chez moi »
* « on peut mettre un délai »
* « on peut simplement cacher l’élément »
* « on peut simuler la réponse »
* « ce n’est qu’un problème d’interface »

Tu dois déterminer précisément si le problème vient du code, de la base de données, du cache, de l’authentification, de l’état frontend, de l’environnement ou de plusieurs éléments.

---

# 2. REPLIT ≠ PRODUCTION

Respecte strictement cette architecture :

* **Replit = environnement de développement**
* **GitHub = source/version du code**
* **Render = environnement de production**

Ne modifie jamais le comportement de production pour contourner un problème uniquement présent dans Replit.

Ne crée aucune condition du type :

* if Replit
* if development → comportement différent
* if Render → comportement différent

sauf nécessité technique réelle et explicitement justifiée.

Si un problème semble venir de l’environnement, démontre-le avec des vérifications concrètes.

Les corrections doivent être compatibles avec le code réellement destiné à être déployé sur Render.

---

# 3. PROBLÈME N°1 — CRÉATION D’ENTREPRISE DEPUIS LA PAGE PUBLIQUE

Actuellement, lorsqu’une entreprise est créée depuis la page publique/accueil, elle **n’apparaît pas dans MAXIMUS → Demandes**.

Corrige définitivement ce flux.

Flux attendu :

PAGE PUBLIQUE
↓
formulaire création entreprise
↓
validation frontend
↓
API/backend
↓
création réelle de la demande dans la base de données
↓
statut = PENDING
↓
MAXIMUS → DEMANDES
↓
la demande apparaît
↓
super administrateur peut APPROUVER ou REFUSER
↓
si APPROUVÉE → entreprise active
↓
si REFUSÉE → entreprise refusée avec statut cohérent

Audit obligatoire :

* formulaire
* validation
* API
* route
* contrôleur
* service
* modèle
* migration
* statut
* relations
* permissions
* requête de MAXIMUS → Demandes
* filtres
* pagination
* cache
* état React
* éventuel React Query/SWR
* doublons
* gestion des erreurs.

La création publique doit utiliser la même logique métier fiable que les autres mécanismes de création.

**Ne simule jamais une demande dans le frontend.**

La demande doit exister réellement dans la base.

Ajoute une protection contre les doubles soumissions.

Une entreprise créée depuis la page publique doit être visible dans MAXIMUS après actualisation complète de la page et nouvelle session.

---

# 4. APPROBATION / REFUS

Vérifie entièrement le workflow.

APPROUVER doit :

* modifier réellement le statut en base ;
* activer correctement l’entreprise ;
* conserver les relations ;
* respecter les permissions ;
* mettre à jour les écrans concernés ;
* ne pas créer de doublons.

REFUSER doit :

* modifier réellement le statut ;
* conserver éventuellement la raison du refus si le modèle le prévoit ;
* empêcher l’entreprise d’être considérée comme active.

Aucune action ne doit afficher « succès » si la base de données n’a pas réellement été modifiée.

---

# 5. PROBLÈME N°2 — ENTREPRISE SUPPRIMÉE MAIS ENCORE ACCESSIBLE

C’est un **problème de sécurité critique**.

Lorsqu’une entreprise est supprimée, une ancienne session, ancienne URL ou ancien contexte peut encore permettre d’ouvrir son administration.

Cela doit être impossible.

Après suppression :

* ancienne URL → accès refusé
* ancienne session → accès refusé
* ancien token → accès refusé
* refresh token → invalidé si nécessaire
* ancien company_id → refusé
* API → refusée
* dashboard → refusé
* modules → refusés
* administration → refusée
* bouton navigateur « retour » → aucune donnée protégée accessible
* accès direct à une route → refusé
* tentative via API → refusée.

Ne te contente surtout pas de rediriger côté React.

**La sécurité doit être appliquée côté backend.**

Audit :

* sessions
* JWT
* refresh tokens
* cookies
* localStorage
* sessionStorage
* middleware
* guards
* permissions
* contexte entreprise
* routes
* API
* cache
* relations DB
* suppression/soft delete éventuel.

Après suppression, chaque requête protégée doit vérifier que l’entreprise existe encore et qu’elle est accessible.

Si nécessaire, invalide les sessions/tokens liés à l’entreprise.

Empêche également les accès à des données orphelines.

MAXIMUS est multi-tenant.

**AUCUNE entreprise ne doit pouvoir accéder aux données d’une autre entreprise.**

Vérifie toutes les ressources :

* utilisateurs
* administrations
* rôles
* permissions
* modules
* produits
* catégories
* stocks
* ventes
* achats
* clients
* fournisseurs
* dépenses
* finances
* présences
* commandes

Le backend doit déterminer et vérifier le contexte de l’entreprise.

Une entreprise A ne doit jamais pouvoir récupérer les données de B simplement en modifiant un ID dans une URL ou une requête API.

Teste explicitement ce scénario.

# 9. PROBLÈME N°4 — ADMINISTRATIONS IMMÉDIATES MAIS MODULES LENTS

Actuellement, après une opération, les administrations apparaissent rapidement alors que les modules mettent du temps à apparaître.

**INTERDICTION ABSOLUE d’utiliser `setTimeout` pour masquer le problème.**

Cherche la cause réelle.

Audit :

* appels API
* requêtes parallèles
* transactions
* ordre des opérations
* cache
* invalidation
* React state
* React Query/SWR
* refetch
* loading states
* lazy loading
* dépendances des composants
* appels API multiples
* race conditions
* synchronisation backend/frontend.

Si une création retourne un succès, le frontend doit disposer d’un état cohérent avec la base.

Utilise une vraie stratégie :

* invalidation correcte du cache
* refetch ciblé
* mise à jour d’état fiable
* réponse backend complète
* transaction lorsque nécessaire
* événement ou mécanisme de synchronisation approprié.

Après création/activation d’un module, il doit apparaître correctement sans attendre artificiellement plusieurs secondes.

# 17. GESTION DES ERREURS

Une erreur backend doit produire une vraie erreur côté frontend.

Interdiction de :

* afficher « succès » après un échec ;
* avaler les exceptions ;
* retourner HTTP 200 pour une opération échouée ;
* masquer une erreur ;
* faire croire qu’une donnée existe alors qu’elle n’existe pas.

Les erreurs doivent être :

* compréhensibles ;
* cohérentes ;
* exploitables ;
* correctement journalisées côté serveur sans exposer de secrets.
