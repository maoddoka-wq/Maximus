Je veux que tu réalises maintenant un AUDIT COMPLET DE LA PRODUCTION de mon application MAXIMUS actuellement déployée sur Render.

IMPORTANT : je ne veux pas un simple audit du code Replit. Je veux comprendre et corriger les problèmes RÉELS qui existent actuellement en production sur Render.

OBJECTIF :
Faire correspondre exactement le code, la configuration, la base de données et le comportement de Replit avec ce qui fonctionne réellement sur Render.

PHASE 1 — ENVIRONNEMENT PRODUCTION
Analyse la configuration de production et vérifie :

- Runtime utilisé
- version PHP/Node/Laravel
- commandes Build et Start
- variables d'environnement nécessaires
- configuration APP_ENV / production
- URL principale de l'application
- URL/API backend
- configuration CORS
- configuration des sessions
- cookies et domaine
- HTTPS
- stockage/fichiers
- cache
- queue/workers si utilisés
- cron/jobs si utilisés
- connexion PostgreSQL
- migrations
- configuration des services externes

Ne révèle jamais les valeurs secrètes des clés API, mots de passe ou tokens. Vérifie seulement leur présence, leur nom et leur cohérence.

PHASE 2 — LOGS RÉELS RENDER
Analyse les logs de production Render et recherche :

- erreurs HTTP 4xx/5xx
- exceptions Laravel/Node
- erreurs PostgreSQL
- erreurs de session/authentification
- erreurs CORS
- erreurs de callback
- erreurs API externes
- timeouts
- erreurs intermittentes
- erreurs liées aux variables d'environnement
- erreurs de routing
- erreurs de queue/worker

Ne te contente pas de corriger la dernière erreur visible. Cherche les causes racines.

PHASE 3 — COMPARAISON REPLIT / RENDER
Compare :

- code actuellement présent dans Replit
- code réellement déployé
- migrations
- variables/configuration nécessaires
- routes
- endpoints API
- frontend/backend
- versions et dépendances

Détermine s'il existe un décalage entre le code testé dans Replit et celui exécuté sur Render.

PHASE 4 — BASE DE DONNÉES
Analyse la structure PostgreSQL de production :

- tables
- colonnes
- relations
- contraintes
- index
- migrations
- données nécessaires au fonctionnement

Vérifie particulièrement les incohérences pouvant provoquer des erreurs applicatives.

IMPORTANT :
Ne supprime, ne modifie et ne migre aucune donnée de production sans mon autorisation explicite.
Si un accès à la BDD de production est disponible, commence par une analyse en lecture seule.

PHASE 5 — AUTHENTIFICATION ET REDIRECTIONS
Teste et analyse tout le parcours :
connexion → session → navigation → API → déconnexion → redirection.

Vérifie particulièrement pourquoi certaines redirections peuvent renvoyer vers /login alors que l'utilisateur devrait retourner vers sa boutique, son espace client ou la page de paiement.

Analyse :

- middleware
- guards
- sessions
- cookies
- domaines
- URLs
- redirects HTTP
- expiration de session
- état utilisateur après retour d'un service externe.

PHASE 6 — DIAMANOPAY
C'est une priorité.

Analyse le parcours complet :

CLIENT
→ commande
→ création du paiement
→ Diamanopay
→ paiement
→ callback/webhook
→ vérification du paiement
→ mise à jour de la commande
→ retour vers le client
→ page de confirmation.

Le problème actuel est intermittent : Diamanopay fonctionne parfois et parfois l'application indique qu'il ne démarre pas.

Analyse les logs correspondant aux deux scénarios :

1. paiement réussi ;
2. paiement échoué.

Compare les deux parcours et identifie exactement ce qui change.

Vérifie également :

- API Diamanopay
- authentification API
- timeout
- URL de callback
- redirect URL
- webhook
- signature/hash si utilisé
- traitement des réponses Diamanopay
- gestion des erreurs
- sessions/cookies
- statut de commande
- idempotence
- concurrence
- timeouts réseau.

Ne remplace pas le problème par un simple message d'erreur générique. Corrige la cause réelle.

PHASE 7 — TESTS DE PRODUCTION
Effectue des tests contrôlés sur les fonctionnalités critiques.

Pour chaque problème trouvé, donne :

- gravité : CRITIQUE / ÉLEVÉE / MOYENNE / FAIBLE
- symptôme
- cause racine
- fichier concerné
- ligne/fonction concernée
- environnement concerné
- preuve provenant des logs ou du comportement réel
- correction recommandée
- risque de la correction.

PHASE 8 — CORRECTIONS
Après avoir terminé le diagnostic, corrige les problèmes réellement identifiés dans le code.

RÈGLE ABSOLUE :
Ne fais pas de modifications arbitraires uniquement parce qu'elles "pourraient" résoudre le problème.

Chaque modification doit être reliée à une cause identifiée.

Après chaque correction :

- vérifie le code
- vérifie les routes
- vérifie les migrations si nécessaire
- vérifie les dépendances
- vérifie qu'aucune fonctionnalité existante n'est cassée.

PHASE 9 — RAPPORT FINAL
À la fin, produis un rapport avec :

1. État général de la production
2. Problèmes critiques
3. Problèmes importants
4. Problèmes mineurs
5. Causes racines identifiées
6. Corrections effectuées
7. Corrections restant à faire
8. Variables/configurations Render à vérifier
9. Tests effectués
10. Risques restants
11. Recommandations pour rendre MAXIMUS stable en production.

IMPORTANT :
Tu travailles sur une application SaaS multi-entreprises. La sécurité et l'isolation des données entre entreprises sont prioritaires.

Ne supprime aucune donnée de production.
Ne réinitialise aucune base.
Ne désactive aucune sécurité pour faire fonctionner un test.
Ne masque aucune erreur.
Ne considère pas le travail terminé tant que tu n'as pas identifié la différence entre les problèmes observés sur Render et le comportement attendu du code.

Commence par le DIAGNOSTIC et les preuves. Ensuite seulement, applique les corrections nécessaires.
